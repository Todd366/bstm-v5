# BSTM Activation — Audit & Build Proposal (2026-10-12)

Scope: repo at commit 706964a, live Vercel deployment, live Supabase `activation` schema.

## 0. Production status

`https://bstm-v5.vercel.app/health` returns 500. The app itself is running (structured error + request_id returned), so this is not an import crash. The failure is inside the DB call. Supabase is ACTIVE_HEALTHY, schema intact (11 tables), env vars unchanged since August. Vercel truncates the traceback, so the exact exception is unreadable. Fix: leak-proof connections, and make `/health` report the DB error class. Root cause is read from the first post-fix response.

## 1. Bugs (confirmed from code / live data)

| ID | Sev | Finding |
|----|-----|---------|
| B1 | P0 | `/health` 500 in production, undiagnosed (above). `/health` also couples liveness to DB and publicly leaks row counts. |
| B2 | P0 | `get_connection()` leaks the connection if `SET search_path` fails after connect. Under errors this exhausts the Supabase session-pooler client limit shared with the marketplace app. |
| B3 | P1 | `POST /opportunities` accepts `department` and `budget` but `create_business_opportunity` drops them. Budget is always 0, so revenue distribution on completion never runs. |
| B4 | P1 | Unique index on `lower(youth.name)`: two people with the same name (common in Botswana) cannot register. Registration also reveals whether a name or email exists. |
| B5 | P1 | Any non-UUID id (`GET /youth/abc`) raises a Postgres cast error → 500 instead of 404/422, on every `{id}` route. |
| B6 | P1 | `apply` flips the opportunity to `Assigned` on the first application. One applicant locks everyone out; a script can lock every opportunity. |
| B7 | P1 | Race conditions: no row locks in `create_assignment`, `accept`, `apply_progression` (lost score updates, double assignment). |
| B8 | P1 | Login timing leaks which emails exist (no dummy hash when email is unknown), contradicting the code comment. |
| B9 | P1 | Tests truncate every table in whatever `BSTM_DATABASE_URL` points at. The only DB is production. One local `pytest` run wipes live data. |
| B10 | P2 | Matching: substring `LIKE` ("ai" matches "retail"), returns one row per matching capability (duplicates), ignores location, availability, equipment. Department opportunities (no business) never match. |
| B11 | P2 | Rate limit 5 registrations/IP/hour breaks shared mobile (CGNAT) and school/hub connections; login has no per-account limit. |
| B12 | P2 | PBKDF2 at 260k iterations (current guidance 600k), no hash upgrade path, no max password length, no email verification, no password reset. JWT 30 days, no revocation. |
| B13 | P2 | No pagination on list routes (`/youth`, `/opportunities`, `/businesses`) — full-table dumps. |
| B14 | P2 | `GET /youth/{id}`, `list_youth` expose `SELECT *` incl. email and intake (financial answers). Admin-key only, but no field policy. |
| B15 | P2 | `set_audit_status` on a missing business updates nothing silently, no activity log. |
| B16 | P2 | CLI (`app/api/cli.py`) is broken since auth change (`activate_youth` needs email/password). Dead duplicates: `youth_service.list_youth`, `business_service.list_businesses`, `core/ids.py`, `core/time.py`, `schemas/`. |
| B17 | P3 | Static files served by a Python function (cold start + DB driver load for a CSS file). No CDN caching, no security headers, CORS `*`. |
| B18 | P3 | Pinned `fastapi<0.100` / `pydantic<2` (known CVEs in the bundled Starlette), unused `python-multipart`, `sqlalchemy`, `alembic`. No lockfile. Termux limits leaked into production pins. |

## 2. Missing wiring (backend exists, UI or flow does not)

| ID | Gap |
|----|-----|
| W1 | Catalog has 1 capability. A new youth has nothing to claim, so discovery returns nothing. No catalog endpoint for the UI. |
| W2 | Registration collects interests and skill level but never creates `youth_capabilities`. |
| W3 | Registration returns no token; the person must log in again straight after. |
| W4 | After apply, nothing a youth can do: no accept/decline/withdraw, no start/submit trial, no evidence submit (`/me/*` only reads). The whole journey stops at "Pending". |
| W5 | Frontend never calls `/me/opportunities`, `/me/opportunities/{id}/apply`, `/me/capabilities`. No browse, apply, claim, or trial screens. |
| W6 | Businesses have no login or ownership: Door Two creates a record that nobody can manage, and posting an opportunity needs the admin key. |
| W7 | No admin console: review, verify capability, select applicant, complete trial are curl-only. |
| W8 | Door Three (field audit) and `mockDiagnosis()` are local-only. Frontend department list (30, hyphen/em-dash names) differs from backend `DEPARTMENTS`. |
| W9 | `revenue` is a number on `youth`; no ledger, no payout, no payment provider. |
| W10 | `learning_score`, `reputation_score` never move. |

## 3. Frontend defects

- Bootstrap clears the token on any failure including a dropped network → logs the person out on flaky mobile data. Only a 401 should do that.
- User text is injected unescaped (wizard `value="..."`, Kgotla title, business result) → self-XSS; token sits in `localStorage`.
- Google Fonts, no offline/retry states, no loading skeletons, no data-light mode; no Setswana.
- Dashboard uses `door` cards for everything; no navigation, no empty-state guidance, no next-action prompt.

## 4. Repo hygiene

Untracked `bstm_v5.zip` in the repo; tracked `patch1/2.sh`, `part1-3.sh`, `cleanup_v5.sh`, `snapshot_v5.sh`, a 71 KB audit txt; README still says SQLite/SQLAlchemy; `.gitignore` has duplicates and no `*.zip`; CI runs 11 tests only.

## 5. Proposal and build order

**Phase 1 — Stabilise (now)**
1. Connection layer: no leaks, `options=-c search_path`, short timeouts. `/health` = liveness (no DB), `/ready` = DB check returning the error class.
2. Fix B3, B4, B5, B6, B7, B8, B11, B12, B13, B15. Migration: drop name uniqueness, seed capability catalog, indexes.
3. Test isolation: tests build a throw-away schema from `migrations/` and never touch `activation`. Add DB-free unit and route tests; CI runs them.
4. Security headers, body-size limit, CORS from env, input limits.

**Phase 2 — Complete the journey**
5. Registration returns a token and claims chosen capabilities (W1–W3).
6. `/me/*` lifecycle: assignments (accept/decline/withdraw), trials (start/submit), evidence submit, skills (W4).
7. Matching v2: word-boundary, deduped, location-aware, availability/equipment aware (B10).
8. Frontend rebuilt around that journey: Home, Opportunities, My Work, Evidence, Skills; offline-safe, escaped, system fonts, mobile-first (W5, section 3).

**Phase 3 — Operate it**
9. Business accounts and own-opportunity posting (W6). Admin console for review/verify/select/complete (W7). Field audit table and screen (W8).
10. Learning/reputation scoring (W10). Setswana/English toggle.

**Phase 4 — Money**
11. Payment provider shortlist for Botswana with Absa personal-account onboarding; ledger table and payout flow (W9).

**Delivery constraint:** this sandbox cannot push to GitHub (token invalid). Each phase is delivered as a tested git patch plus zip; applying it from Termux is two commands. Additive migrations are applied directly to Supabase and recorded in `migrations/`.
